# Measurement lessons

## Comparable workloads

Use release builds/images and the actual production middleware/proxy path. Pin app/dependency/
load-generator versions, same data/user/status, CPU placement and service warm state. Alternate
order across multiple rounds and retain every raw round, not only the best. Count successful
expected responses; record redirects/errors/timeouts separately. A faster error response is
not a faster application.

Measure populated routes and writes with realistic rich text/attachments and callback fanout.
Distinguish microbenchmarks (escaping, row decoding, recognition, compression, build scripts)
from total HTTP improvement. Warmed MySQL SQL logs must exclude statement preparation and restore
log configuration afterwards. Keep logs isolated from production and redact actual credentials.

Memory accounting should identify RSS/PSS versus cgroup usage, inactive cache exclusions,
allocator arenas and kernel socket buffers. Startup should measure to meaningful readiness,
not only exec or a stub /up. Report image compression and native media/runtime dependencies.

## Gains that transferred

Both ports benefited from shared compatibility shims, borrowed rendering data/direct buffers,
explicit columns with safe positional fallback, efficient route prefiltering, fewer duplicate
allocations and bounded adaptive buffers. Campfire additionally benefited from its SQLite
reader/writer design, reusing page/compressed pieces, CRC reuse and broadcast-frame reuse.
Backpack's MySQL workload needed query concurrency/coalescing and its own callback transaction
fixes. These are investigation starting points, not universal tuning requirements.

Dependency pruning can be a build/maintenance win without an HTTP win. Removing fancy-regex
and Latin-1 copies sped Campfire's asset build script about 9.8x while preserving generated bytes.
Keep those numbers labeled build-script time. Jemalloc and zlib-rs SIMD had measured runtime
reasons: blindly disabling defaults can remove an accidentally enabled performance feature.
Confirm the final feature graph and benchmark the configuration you actually ship.

## Connection-capacity forecasts

A CPUQuota-limited Ryzen loopback test is not a Raspberry Pi benchmark. Loopback excludes NIC
bandwidth and often TLS/proxy overhead. Process memory excludes Linux socket buffers. One user
with many sockets does not exercise distinct membership records, unread-user streams, auth or
per-user state. Validate on the real target and count actual unique users and room topology.

Forecast with explicit RAM budget, per-connection process+kernel memory, file descriptor/accept
settings, TLS, message size, senders' behavior, room fanout and NIC capacity. Human readers
usually post less than synthetic senders, but burst behavior and large announcements matter.
Do not present extrapolations as measured capacity. 10GbE addresses only one bottleneck.

HTTP/3 or io_uring is not a prerequisite for a large idle connection count. Adopt a protocol
or I/O backend when profiling and deployment/client requirements show an actual gain, then
retest latency, backpressure, memory, crypto, compatibility and failure handling.
